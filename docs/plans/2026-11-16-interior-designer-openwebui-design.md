# Interior Designer in Open WebUI — design

**Date:** 2026-11-16 · **Status:** built and installed; verified over the API (steps 1–3 below),
browser check by a person pending
**Context:** `deploy/openwebui/` · `docs/plans/2026-07-08-lan-chat-frontend-openwebui-design.md`

## Goal

A model called **Interior Designer** in the Open WebUI model menu, next to Qwen. Anyone with an
account (household and guests) uploads a room photo, says what they want, and gets back a design
concept in text plus a photo-realistic render of their own room restyled.

## The shape

```
browser ─▶ Open WebUI (weebeastie)
             model menu: "Interior Designer"  (workspace preset, public read)
               base model: gpt-5.6-sol        (2nd OpenAI connection, Responses API, admin-only as a raw model)
               skill:      interior-design    (inlined into the system prompt every turn)
               tool:       render_design      (custom; calls OpenAI GPT Image)
                                │
                                ├─▶ api.openai.com/v1/chat/completions   (designer: sees photo, writes concept + instruction)
                                └─▶ api.openai.com/v1/images/edits|generations  (renderer: gpt-image-1.5)
```

Qwen and every other chat are untouched: the local model is not in this path, so a design session
never evicts its warm KV slot.

## Decisions

**Designer = `gpt-5.6-sol`, not the local Qwen.** Qwen3-Coder is text-only and cannot see the
photo. A local VLM would be CPU-only (no VRAM left) at ~3 t/s. DeepSeek V4.1-Flash can see but
cannot render, and keeps data in the PRC; Anthropic has no image model. The room photo goes to
OpenAI anyway for rendering, so an OpenAI designer adds only the conversation text to what leaves.

First built on `gpt-5.4-mini` (accurate room read in 5 s), switched to `gpt-5.6-sol` the same day
for quality. Observed difference on the same photo: mini rendered first and explained after; sol
reads the room, presents the concept in budget tiers with a lighting plan, *then* renders, and
proposed keeping the existing sofa on a mid budget. ~11 s to the tool call, light reasoning
(76 tokens at default `medium` effort).

**The connection uses the Responses API** (`api_type: "responses"`). `gpt-5.6-sol` rejects
function tools with reasoning on `/v1/chat/completions` (HTTP 400: "use /v1/responses or set
reasoning_effort to 'none'"); Open WebUI v0.10.2 can route a connection to `/v1/responses`, and
native tool calling, image input and multi-turn replay all work through it (verified below).

**Renderer = `gpt-image-1.5` via a custom tool, not Open WebUI's built-in image feature.** Read in
the v0.10.2 source, the built-ins have two gaps:

1. The legacy forced path (`chat_image_generation_handler`) sends the user's **raw message** as the
   edit prompt, so the skill never shapes the picture.
2. The native path's `edit_image(prompt, image_urls)` needs the photo's URL, but uploaded images
   reach the model as inline base64 (`middleware.py`, image parts converted before the request),
   so the model has no URL to pass.

`render_design(instruction, source)` closes both: the designer writes the full instruction, and the
tool finds the image itself — the latest render or the latest uploaded photo, from the chat's
stored history. It also owns the controls the built-ins lack: `quality` (the edit endpoint does not
forward one), `input_fidelity`, and a per-user daily cap.

**Global image generation stays OFF.** The tool holds its own key (a tool valve) and does not need
`image_generation.enable`. So no image switch appears on Qwen chats, and the built-in image tools
never reach any model.

**The preset gets no built-in tools and no memory** (`capabilities.builtin_tools: false`,
`memory: false`). With the defaults, native function calling hands the model `search_chats`,
`view_chat`, notes and memory tools, and memory context is injected into the system prompt: an
OpenAI model could read a user's local Qwen chats. Off, only the design chat leaves the house.
Side effect, intended: with built-ins off, Open WebUI inlines the attached skill in full instead of
listing it for `view_skill`, so the skill is always applied.

**Raw OpenAI models stay hidden.** In v0.10.2 a model without a DB entry is visible to admins only;
users see only models with a grant. The connection also allow-lists exactly `model_ids: [gpt-5.6-sol]`, so
even the admin menu stays short. The preset has a public-read grant (`user:*`), so accounts made
later (guests) see it without further setup.

**Task model unchanged** (`TASK_MODEL_EXTERNAL` empty ⇒ titles/tags/follow-ups for a design chat
are generated by `gpt-5.6-sol`). That sends nothing new — the chat already went there — and keeps
title requests off the local single slot.

## Configuration is code

| Piece | File | Lands in |
|---|---|---|
| Skill | `deploy/openwebui/skills/interior-design.md` | Workspace → Skills (id `interior-design`) |
| Tool | `deploy/openwebui/tools/render_design.py` | Workspace → Tools (id `render_design`) |
| Preset | `deploy/openwebui/models/interior-designer.json` | Workspace → Models (id `interior-designer`) |
| Installer | `deploy/openwebui/install_interior_designer.py` · `make install-designer` | all of the above + the connection + the tool's key |

The installer is idempotent (create-or-update) and reads `OPENAI_API_KEY` + `OPENWEBUI_API_KEY`
from the repo's `deploy/openwebui/.env`. Open WebUI's DB stays authoritative at runtime, as for
every other setting (the compose env only seeds first boot).

## Privacy — what leaves the house

Per design chat, to OpenAI (US): the whole conversation on every turn, the photos, and the render
instructions. Not sent: other chats, memories, notes, the RAG index. Nothing is stored in an OpenAI
account in the user's name — the API key is the only identity. OpenAI API data is not used for
training by default; abuse-monitoring retention terms changed during 2025 — **check the current
terms before relying on them**.

## Cost controls

- Tool valves: `quality=medium` (`low` is ~1¢ a render at 1024², `high` several times medium —
  reconfirm on the pricing page), `daily_renders_per_user=20`, one render per reply (system prompt).
- **Set a monthly spend limit on the OpenAI project.** It is the only hard cap; the daily cap is in
  process memory and resets when the container restarts.

## Verification

1. `make install-designer` twice — second run reports updates, no duplicates.
2. `/api/models` as a non-admin lists Qwen + Interior Designer only.
3. A chat through the API with a room photo: the designer calls `render_design`, an image file is
   returned, OpenAI usage shows one edit.
4. In the browser, by a person: upload a photo, ask for a style, iterate once ("make the sofa
   green") — the second render must start from the first render, not from the original photo.

**Results, 2026-11-16.** (1) second run updated in place, no duplicates. (2) by grant inspection:
preset, skill and tool carry `user:*` read; the raw base model has no DB entry ⇒ admin-only.
(3)+(4) through the browser's code path (stored chat, uploaded photo by file id): the designer
called `render_design(source="photo")`, reply + render in ~25 s, room geometry kept; a follow-up
("sage sofa, linen curtains") used `source="latest"` and changed only those two things on the
first render. Not yet done by a person in a browser.

**Re-run on `gpt-5.6-sol` via the Responses API, same day:** same photo and follow-up. Text-first
reply (room read → concept in budget tiers → lighting → paint-sample advice), then
`render_design(source="photo")`; the follow-up ("make the sofa sage green") used
`source="latest"` and changed only the upholstery. Tool calls, the inline photo and the earlier
turn's tool output all replay correctly through Open WebUI's `/v1/responses` path.

Two findings from the run: a bare `/api/chat/completions` call (no stored chat) returns the tool
call unexecuted, so API tests must create the chat the way the browser does; and an image file
referenced as `/api/v1/files/<id>/content` is not resolved for the model — the browser uses the
bare file id.
